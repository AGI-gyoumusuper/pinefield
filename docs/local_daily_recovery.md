# 日次スクレイピングの不足補完

夜20:00〜23:10の既存Windowsタスク20件は、翌日分のGitHub取得を10分間隔で起動します。タスクの終了コード0はGitHubへの起動要求の送信成功です。商品取得の完了は、GitHub上の当日商品JSONとsummaryが現行検査に合格した時点で判断します。

`pinefield-local-recovery-all` は毎日20:30から翌08:00まで30分間隔で起動し、記事制作で商品が固定される前に不足分を補完します。20時以降は翌日分、日付が変わってからは当日分を対象とします。Windowsへログインしておく必要があります。確認・取得ともPythonで行い、AIモデルは呼び出しません。

- 「1件以上の有効データ」と「4投稿分が揃った状態」を別に数えます。4枠分が揃った工場は取得しません。有効な1〜3件は保ち、固定前に限って確認済みの新商品を後ろへ足します。
- 夜間は対象アカウントの最新起動要求に対応するGitHub取得が完了したことを確認します。23:30のEnsureと競合させないため23:25までに終了し、余裕がなければ次回へ回します。日付変更後は通常取得・Ensure・Late Repairの終了を待ちます。
- GitHubが実行中、終了証拠が不足、APIに接続できない場合は取得せず、次回起動で再確認します。
- 既存の工場source固定、アカウント別ロック、同一アカウント・日付の1回限りの取得記録を守ります。
- 1工場が失敗しても、独立した残りの工場を処理します。
- 既存の有効性検査は1〜10件を受け付けます。補充目標は通常工場4件、20番はSwitch 2とPS5各2件です。20番も既に保存された商品を差し替えず、最大10件を守れる範囲で補充します。カテゴリ、価格下限、既投稿・同一商品除外、割引の証拠は緩めません。
- 同時起動はしません。1回の処理は最大3時間、1工場の取得は最大30分です。夜間は23:25の終了境界を優先します。同じアカウント・対象日の取得は1回に限定し、Cloudとの競合で反映を保留した場合は保存候補を再検査して使います。候補の入力条件や台帳が変わった場合は停止して報告します。
- 結果は `D:\_0NOTEKATU\scraping\YYYY-MM-DD\daily-recovery-controller\run-NN\result.json` に保存します。個別の取得物は同日付配下の `local-recovery-accountN\run-NN` に保存します。ASIN台帳は成果物フォルダへ複製しません。

設定の再登録は、正本リポジトリの `scripts\Install-LocalScrapeRecoveryTask.ps1` を実行します。夜間準備を含む読み取り確認は `python scripts/recover_missing_daily_sources.py --nightly-preparation`、不足分の実行は同コマンドに `--execute` を付けます。引数なしの旧導線は当日・欠損のみの確認を維持します。インストーラーは翌日20:30を開始日時にするため、その夜から使う場合は検証後に既存タスクの開始日を当日に合わせます。

初回scraperも、最初の詳細確認後に4投稿分が揃わなければ、既に集めた未確認候補から最大24商品・240秒の追加確認を1回だけ行います。商品を確認できなくても先に得られた有効商品は保存します。追加確認は入力商品を工場へ渡す前の処理で、A/BへAmazon再確認を追加するものではありません。

GitHub側の失敗候補と公開検索ページの診断は、当該Actions実行のartifactに3日間保存します。候補データを正本へ反映するのは、従来どおり検査に合格した場合だけです。
