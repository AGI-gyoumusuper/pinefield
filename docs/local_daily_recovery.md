# 日次スクレイピングの不足補完

夜18:00〜21:10のWindowsタスク20件は、翌日分のGitHub取得を10分間隔で起動します。タスクの終了コード0はGitHubへの起動要求の送信成功です。商品取得の完了は、GitHub上の当日商品JSONとsummaryが現行検査に合格した時点で判断します。

`pinefield-local-recovery-all` は毎日18:30から翌08:30を終端とする14時間の範囲で、10分間隔の起動機会を設けます。記事制作で商品が固定される前に不足分を補完します。18時以降は翌日分、日付が変わってからは当日分を対象とします。Windowsへログインしておく必要があります。確認・取得ともPythonで行い、AIモデルは呼び出しません。

- 「1件以上の有効データ」と「4投稿分が揃った状態」を別に数えます。4枠分が揃った工場は取得しません。有効な1〜3件は保ち、固定前に限って確認済みの新商品を後ろへ足します。
- 夜間は対象アカウントの最新起動要求に対応するGitHub取得が完了したことを確認します。23:30のEnsureと競合させないため23:25までに終了し、余裕がなければ次回へ回します。日付変更後は通常取得・Ensure・Late Repairの終了を待ちます。
- 開始時刻と確認間隔の前倒しは、最終番号も23:25より前に補完する時間を確保するためです。GitHubの定時修復の開始遅延を解消する変更ではなく、夜間に揃わなかった分は従来どおり修復完了を待ちます。10分間隔は確認の頻度であり、同じ商品を何度も取り直す設定ではありません。
- GitHubが実行中、終了証拠が不足、APIに接続できない場合は取得せず、次回起動で再確認します。
- GitHubのEnsureでも、通常取得の稼働状態を確認できない場合や待機時間を超えても実行中の場合は、その修復を停止します。稼働中の全ステータスをページ分割して確認し、古い実行や最新20件の外にある実行を見落として重複取得しないようにします。1〜5番の共有workflowは安全側に全体の終了を待ちます。
- 既存の工場source固定、アカウント別ロック、同一アカウント・日付の1回限りの取得記録を守ります。
- プライム先行セールから本祭へ切り替わる日は、対象日のセール段階が実際に始まるまで `WAIT / prime_event_wait_for_target_phase` とし、取得回数を消費しません。前日の先行表示を本祭へ書き換えません。
- 切替対応前に取得回数を消費した場合は、保存された初回結果・商品0件・前段階の表示による不一致を照合でき、対象段階へ移行済みで、当日sourceが未固定の場合だけ、段階切替用の取得を1回許可します。旧attempt・結果は保持し、専用の排他的な取得記録で重複を防ぎます。通常の失敗や確認画面停止に、この例外を広げません。
- 1工場が失敗しても、独立した残りの工場を処理します。
- 既存の有効性検査は1〜10件を受け付けます。補充目標は通常工場4件、20番はSwitch 2とPS5各2件です。20番も既に保存された商品を差し替えず、最大10件を守れる範囲で補充します。カテゴリ、価格下限、既投稿・同一商品除外、割引の証拠は緩めません。
- 同時起動はしません。1回の処理は最大3時間、1工場の取得は最大30分です。夜間は23:25の終了境界を優先します。同じアカウント・対象日の取得は1回に限定し、Cloudとの競合で反映を保留した場合は保存候補を再検査して使います。候補の入力条件や台帳が変わった場合は停止して報告します。
- 結果は `D:\_0NOTEKATU\scraping\YYYY-MM-DD\daily-recovery-controller\run-NN\result.json` に保存します。個別の取得物は同日付配下の `local-recovery-accountN\run-NN` に保存します。ASIN台帳は成果物フォルダへ複製しません。

設定の再登録は、正本リポジトリの `scripts\Install-LocalScrapeRecoveryTask.ps1` を実行します。夜間準備を含む読み取り確認は `python scripts/recover_missing_daily_sources.py --nightly-preparation`、不足分の実行は同コマンドに `--execute` を付けます。引数なしの旧導線は当日・欠損のみの確認を維持します。インストーラーは翌日18:30を開始日時にし、インストール時の過去時刻を追いかける意図しない起動を避けます。進行中の同一日付の取得を起動し直さず、実タスクの適用日と稼働状態を確認して切り替えます。

初回scraperも、最初の詳細確認後に4投稿分が揃わなければ、既に集めた未確認候補から最大24商品・240秒の追加確認を1回だけ行います。商品を確認できなくても先に得られた有効商品は保存します。追加確認は入力商品を工場へ渡す前の処理で、A/BへAmazon再確認を追加するものではありません。

12番と14番は、価格・割引等で選別する前の候補をカテゴリごとに最大100件まで集めます。従来の先頭10件での打ち切りにより、後方の条件適合商品を取りこぼしていたためです。検索は既存の最大2ページまで、最終保存は最大10件までとし、価格条件・割引検証・既投稿除外は維持します。

詳細ページの確認画面で停止した記録（`detail_challenge`）がある場合、Ensureは別プロセスで全巡回を繰り返しません。既に検査に合格する商品があれば保存し、0件など不合格の場合は診断保存後に実行前の状態へ戻して失敗を報告します。確認画面以外の一時障害は従来の最大3回の再試行を維持します。これにより、確認画面で止めた直後に同じ取得を再開する不整合を防ぎます。

GitHub側の失敗候補と公開検索ページの診断は、当該Actions実行のartifactに3日間保存します。候補データを正本へ反映するのは、従来どおり検査に合格した場合だけです。
